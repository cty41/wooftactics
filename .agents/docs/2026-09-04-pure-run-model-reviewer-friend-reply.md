# 为什么基座模型已经会“看图找错”，还需要生图状态机和多模态 Reviewer？

你的困惑很合理：如果多模态模型能够检查出生图中的错误，为什么这种能力不直接做进生图基座模型？再套一个 Reviewer，是不是只是在重复模型本来就会做的事？

简短答案是：

> 基座模型通常已经具备识别这些错误的能力，但“具备能力”不等于“每次生成时都能稳定执行、记住项目历史并提供可审计保证”。状态机不是创造新的通用智能，而是把模型已有但不稳定的能力组织成可靠的工程流程。

## 1. 生成和检查是两种不同难度的任务

生成时，模型需要同时满足许多目标，例如：

- 保持同一个角色身份；
- 转换到新的三维观察方向；
- 保持卡通画风；
- 保持规定身体结构；
- 放置装备；
- 处理手、身体和装备的遮挡；
- 维持指定尺寸和构图。

这些目标可能相互竞争。模型可能理解“武器在身体后面”，又同时倾向于“尽量把武器画完整”，最后把被身体遮挡的武器上下两端都画出来，使它在人眼中像断成两截。

审核已经存在的图片则简单得多：Reviewer 可以逐项检查“有没有胳膊”“身体是不是胶囊体”“刀是否读成断裂”“环首角度是否过正”。

这类似于：

- 作者会写出错字，但校对时容易发现；
- 程序员会写出 bug，但编译器、测试和 Code Review 能发现；
- 画师会画错透视，Art Director 可以在成图后指出。

`Self-Refine` 等研究也表明，即使不训练新模型，在推理阶段增加“生成—反馈—修正”循环，也能改善一次性输出。这不代表模型增加了新知识，而是系统给已有能力提供了第二次、结构不同的思考机会。

参考：[Self-Refine: Iterative Refinement with Self-Feedback](https://arxiv.org/abs/2303.17651)

## 2. “知道规则”不等于“能精确控制每个像素”

图像生成具有概率性。模型可能在语言层面理解：

> 这个角色只有直接贴着身体的手爪和脚爪，不应出现胳膊或腿。

但生成过程受到训练分布影响，仍可能把“身体旁边的手爪”补全成常见的“身体—短胳膊—手”。

因此会出现一种看似矛盾的现象：

1. 模型生成了错误结构；
2. 把结果图重新交给多模态模型；
3. 它又能正确指出“这里多出了一段胳膊”。

这说明问题不一定是模型完全不懂，而可能是生成控制精度不足、多个目标冲突，或者生成阶段没有逐项执行检查。

## 3. 通用基座模型不知道项目的私有历史

通用模型不会天然知道某个具体项目中已经确认的规则，例如：

- 胶囊角色不能出现任何胳膊或腿；
- 手爪和脚爪必须以宽接触面直接连接主体；
- 某把环首唐刀已经批准了特定的三维投影；
- 装备宁可大部分不可见，也不能为了展示而破坏空间关系；
- 某个旧角色素材已经退休，永远不能再作为输入；
- 哪些错误已经被人工重复否决；
- 哪些例外只适用于死亡、飞行或特定动作。

这些是私有、动态、版本化的项目知识。它们不可能预先全部存在于通用模型参数中。

状态机的作用，是把这些知识保存为：

```text
项目规则 + 正反案例 + 当前合同 + 历史人工反馈 + 权限边界
```

然后每次只把与当前任务相关的部分交给 Reviewer。

## 4. 状态机不是让模型更聪明，而是让流程更可靠

完整流程可以理解为：

```text
ImageGen 生成候选
        ↓
确定性程序检查路径、SHA、尺寸、透明度等事实
        ↓
独立多模态 Reviewer 检查视觉拓扑、方向和遮挡
        ↓
明确硬错误可受控重试；不确定问题主动交人工
        ↓
人工进行最终艺术审核
```

各部分职责不同：

- **ImageGen**：提出候选；
- **确定性校验**：验证机器可以证明的事实；
- **多模态 Reviewer**：模拟逐项视觉检查；
- **状态机**：保存历史、限制权限、防止错误资产复用；
- **人工**：决定审美和最终是否批准。

这更像软件开发中的：

```text
写代码 → 编译 → 静态检查 → 自动测试 → 人工 Code Review
```

没有人会因为程序员理论上懂语法，就认为编译器和测试没有价值。

## 5. 为什么要使用独立 Reviewer？

如果同一个模型既生成又审核，可能共享同一个盲点：

```text
生成时认为这种遮挡合理
→ 审核时继续为这种遮挡辩护
→ 再次放过同类错误
```

因此当前方案把职责分开：

- 图像由 GPT Image 模型生成；
- 审核由独立上下文中的 GPT 多模态推理模型执行；
- Reviewer 只能指出问题和请求重试，不能批准资产；
- 最终通过权仍属于人。

独立 Reviewer 仍可能出错，所以还需要：

- 先只记录判断，不自动执行；
- 按具体规则逐项授予自动重试权限；
- 证据不足时主动交给人工；
- 一旦发现漏检或误杀，立即撤销对应规则的自动权限。

## 6. 这里的“经验积累”并不等于训练模型

更准确的名称不是“自学习”，而是：

> **受控经验积累。**

它不会：

- 更新 GPT 的模型参数；
- 微调图像生成模型；
- 自动把聊天内容变成训练数据；
- 让通用模型永久记住这个项目。

它实际做的是：

```text
人工指出新问题
→ 系统生成规则或案例建议
→ 人工确认适用范围
→ 写入项目自己的规则库
→ 后续审核时检索使用
```

模型只负责提炼建议，不能自行修改正式规则。新规则也不能立即获得自动执行权，必须先在历史正反案例上验证，再由人工授权。

因此它属于“外部记忆和案例驱动的在线规则适配”，不是基座模型训练。

## 7. Atlas 世界模型和这个方案有什么关系？

World Labs 的 Atlas 是一种原生处理文本、图片、视频和 3D 的空间世界模型。其重点是把图片放入共享三维空间上下文中，生成具有更好多视角一致性的内容。

参考：[Atlas: A World Model for Spatial Intelligence](https://www.worldlabs.ai/blog/atlas)

它与当前问题确实有相似之处。比如把一把刀从右下视角转换为左上视角，需要理解：

- 刀的三维长轴如何投影；
- 环首正面应该变成多窄的椭圆；
- 柄、护手和刀鞘如何同步缩短；
- 同一个物体从不同相机角度仍应保持身份。

世界模型如果能稳定完成这种转换，会显著减少第一轮空间错误。

但它解决不了全部项目规则。即使空间投影完全正确，它也不会自动知道：

- 角色必须是特定胶囊体；
- 禁止胳膊和腿；
- 某个装备目前延期；
- 某份历史素材已经退休；
- 装备应该克制展示；
- 人工对风格和可爱程度的具体偏好。

所以两者关系是：

- 世界模型提高生成阶段的空间正确率；
- 状态机和 Reviewer 保证项目规则、历史经验、审核权限和证据链。

更强的基座模型会减少 Reviewer 发现的问题，但不会自动消除项目级验证的必要性。

## 8. 如何证明这套闭环不是多此一举？

不能只凭直觉认定 Reviewer 有用，应该做对照验证。

### Prompt-only 基线

```text
相同合同 + 相同参考图 + 相同提示词
→ 生成候选
→ 直接人工审核
```

### Reviewer 闭环

```text
相同合同 + 相同参考图 + 相同提示词
→ 生成候选
→ 确定性检查
→ 多模态 Reviewer
→ 必要时受控修正
→ 人工审核
```

比较的不是“审美总分”，而是：

- 已知硬错误进入人工审核的次数；
- 同类错误重复发生的次数；
- Reviewer 漏检次数；
- Reviewer 误杀正确候选的次数；
- 人工需要重复指出硬错误的次数；
- 每个可审核候选消耗的生图轮次；
- Reviewer 主动交人工的情况。

如果 Reviewer 闭环没有减少重复硬错误，或者误杀导致更多无效生图，就不应该扩大它的自动权限。

## 9. 最终结论

“基座模型应该已经有这个能力”是正确的，但这并不否定状态机，反而解释了为什么这个方案可行：Reviewer 正是在调用基座模型已经具备的视觉理解能力。

真正需要解决的不是：

> 模型到底会不会看出错误？

而是：

> 如何让这种能力在正确时间、使用正确项目知识、按照明确权限稳定执行，并在出错时可以追溯和撤权？

因此这套方案不是在发明新的通用智能，也不是让模型凭空自我进化。它是在构建一个：

> **由生成器、审核器、确定性状态机、项目外部记忆和人工终审共同组成的生成可靠性系统。**

如果未来的世界模型或图像生成模型显著提高空间一致性，这套系统的自动重试次数会下降；但项目规则、历史案例、证据链和人工最终裁决仍然有价值。
