# Godot Content Migration

## Quick Reference

Flow: frozen source DTO/receipt → `ContentDraft` → Application diagnostics/snapshot → staging → ResourceSaver/PackedScene → catalog/manifest.

`ContentId` is the business identity. Unity GUID/LocalFileId locates source only; `uid://` locates generated Godot resources.

## When to use

Use for any migration batch, exporter, converter, manifest, catalog, ResourceSaver or ownership/status transition.

## Workflow

1. Bind the batch to `unity-final-2026-08-08`, source commit and source hashes.
2. Read only the frozen DTO, receipt, Golden or Oracle bound by the batch; do not restore a live legacy editor/export path.
3. Validate strict lowercase `ContentId`, schema, type and references through Application.
4. Generate into staging with target hash and prior UID; refuse to overwrite an unexpected manual target change.
5. Save through ResourceSaver/Editor API or a tested converter. For a new path generated by standalone headless C#, register a stable `CreateIdForPath` UID, persist it with `ResourceSaver.SetUid`, and preserve the ledger UID on repeats.
6. Atomically update the batch ledger. Re-run and prove byte/semantic idempotency.
7. After standalone generation, run a headless Editor filesystem scan before a separate Runtime process validates new UID paths.
8. Keep ownership separate from processing status; only human-accepted full categories become `GodotOwned`.

## Examples

- Poison Spear Lv1 remains `UnityOwned` while its batch can reach `Validated`.
- A regenerated `.tres` retains the catalog UID and produces no semantic diff on a second run.

## Anti-patterns

- Do not hand-edit `.tres` or `.tscn`.
- Do not make migration DTOs runtime inputs.
- Do not equate `Generated` with parity or visual acceptance.

## Checklist

- [ ] Frozen source/hash/exporter version recorded.
- [ ] Draft diagnostics passed.
- [ ] UID, reference and target hash validated.
- [ ] Failure rollback and repeat-run idempotency tested.
- [ ] Batch status and ownership updated independently.
