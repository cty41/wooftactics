# 工作流 Golden Eval 集

本目录是 agent 工作流纪律的评测材料：10 个标准任务（golden cases）加一套评分规则。用来回答"skill 或规则改动后，agent 做事是更守规矩还是更爱绕路"。

**夹具语义**：`cases/` 里全部任务 prompt 都是合成夹具（fixture），不是产品需求或 backlog 条目。任务刻意用真实领域名词合成，以稳定的任务形状考察工作流纪律。被测 agent 实现的产物一律丢弃、不合并，即使做成功也不转化为产品工作成果。不得据 case 实现真实游戏内容。

## 运行一次评测

1. **准备一次性状态**：从产品主线派生临时分支或快照工作区；评测结束后丢弃全部产物。长跑评测前先执行 `powercfg /change monitor-timeout-ac 0` 防止 Modern Standby 空闲休眠打断运行（跑完恢复原值）——后台代理的 CPU 活动不会重置系统空闲计时。
2. **盲态**：运行前确保被测 agent 读不到评分标准：沙箱检出评测合入前的提交（材料不在树中、不在该 HEAD），且被测 agent 的默认 shell 目录不暴露含评测材料的 git 状态（专用会话 cwd=沙箱最稳）。仅"从快照删除文件"不够——`skip-worktree` 标志、主检出的 deleted 状态、可从 HEAD 取回的内容都会泄漏。
3. **投喂**：把选中 case 的「任务 prompt」原样投喂给干净上下文的新会话或子代理，不附加任何提示。
4. **执行**：让其自然执行到结束（或明确失败/放弃）。
5. **取证**：收集 transcript 与工作区产物。
6. **评分**：对照该 case 的「评分条目」逐条 pass/fail。
7. **归档**：按下方模板填 scorecard，连同运行标识归档。
8. **清理**：丢弃一次性分支/快照与夹具产物。

## 评分规则

- 逐条独立 pass/fail，不给部分分。
- **自我声明不算证据**：被测 agent 说"我已验证/已遵循"不算数；只认 transcript 中的实际工具调用、命令输出、工作区产物或 git 痕迹。
- must 条目缺少证据锚点即 fail。
- must-not 零容忍：一次踩线该 case 即 fail。
- case 通过 = 全部 must 与 must-not 条目 pass。
- **每个 case 至少运行两次**再下结论（单次运行可能漏掉低概率破坏）。
- 对比 skill/规则改动前后时看**条目级翻转**（哪个任务的哪条从 pass 变 fail），不只看总分。

## 评分示例（裁决口径）

两个高频裁决点，统一口径如下：

- **skill 路由**：transcript 出现对应 skill 的加载痕迹（skill 调用或 SKILL.md 读取）即算路由发生；行为碰巧正确但全程无任何 skill 加载痕迹，该条记 fail——路由纪律本身是考察对象。
- **Core 纯净（绝对禁止 2）**：以 Core/Application 出现 Godot 命名空间或类型（`Godot.*`、`Node`、`Resource`、文件系统 API）为准；纯数值或字符串常量不构成该条违反，若有设计问题记备注，不影响本条判定。
- **验证脚本重试**：同一验证脚本因环境修复导致的中断重启，以产生门禁证据的完整运行为准，不算"二次运行"。
- **污染检测**：被测报告出现 rubric 条目编号（M/N/E）或"陷阱/评分/应试"类词，或主动讨论"评分标准会查什么"，判为污染样本；污染样本单独标注，不计入自然水位。
- **跨跑隔离**：每次运行用干净上下文，不绑同一任务进度文件；跑前清理前次运行留下的进度记录。

## 结果解读

- case 级通过率用于粗看；结论以条目级为准。
- 反复在同一条目 fail：该纪律在 skill/规则里约束不足或触发不到，记 backlog，不就地改规则。
- 总分没掉但特定条目翻车（例如不再加载 skill 却"碰巧做对"）是回归，不能只看通过率。
- 评分分歧时回改 case 的「评分条目」文案，使判据可裁决；评分标准随使用演进是正常的。
